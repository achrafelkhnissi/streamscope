# M9 Checks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** expectations checked automatically, live. Each `# @expect` line of a request is evaluated while its response streams. It settles at the earliest event that decides it and never changes afterwards. Its result shows in the panel's Checks tab, as a summary in the panel status line and CodeLens, and as a ✓ / ✗ decoration on the line.

**Architecture:**

- **`src/checks/` (pure):**
  - A compiler splits a check's expression into a boolean **skeleton** (`&&`, `||`, `!`, comparisons, `exists`, `before`, `unique`) and **terms**. A term is a value sub-expression such as `status`, `first(type == "A").id` or `count(type == "B")`.
  - A three-valued evaluator (true, false, unknown) turns the current term states into a verdict and a detail.
- **Terms are evaluated by the capture tracker that already exists:**
  - each term becomes an internal capture `(term) | json`, so it settles with exactly the capture timing (headers, the matching event, or the end of the run);
  - it inherits the capture tracker's budgets, queue, backpressure and child-process hand-off.
- **Counts and `before(…)`:** these need progress during the stream, so the capture tracker gains one hook that reports each new match of a `count(…)` watch.
- **A check tracker per run** combines term results and count progress into verdicts, and runs beside the user's captures through a combined run observer. A check service and registry per request feed the panel, the CodeLens and the editor decorations.

**Tech Stack:** TypeScript 6.0.3, VS Code API 1.101 (`createTextEditorDecorationType`, CodeLens), the M6 webview, Vitest, `@vscode/test-cli`. No new dependency.

## Decisions this plan makes (builder's call, approval of this plan approves them)

1. **What a check is.**
   - **Truth:** the expression's value is true when it is present and neither `false` nor `null`, as for a condition.
   - **Missing operands:** a comparison with a missing operand is false. The detail names the missing value and its reason.
   - **Limit:** a request has at most 64 `# @expect` lines. The 65th is an error diagnostic, like captures.
2. **When a check settles: the earliest event that decides it.** Its expression is evaluated in three-valued logic, true, false or unknown, whenever something it reads becomes known:
   - **Terms settle exactly as captures do.** A term that reads only `status`, `headers` or `cookies` settles when the headers arrive. A term whose only event source is one `first(…)` or `nth(…)` settles when that event arrives. Every other term settles at the end of the run.
   - **Logic:** `&&`, `||` and `!` follow Kleene logic, so `a && b` is false as soon as either side is false, and `!exists(first(type == "RUN_ERROR"))` fails at the first `RUN_ERROR` event.
   - **`exists(x)`:** true when `x` settles present, false when it settles missing.
   - **`count(c)` compared with a number literal:** the running count is a lower bound, decided as follows. The rules mirror for a literal on the left, and every other count comparison waits for the end.

     | Comparison | Settles early when   |
     | ---------- | -------------------- |
     | `> k`      | true once count > k  |
     | `>= k`     | true once count ≥ k  |
     | `< k`      | false once count ≥ k |
     | `<= k`     | false once count > k |
     | `== k`     | false once count > k |
     | `!= k`     | true once count > k  |

   - **`before(a, b)`:**
     - true at the first event matching `a` if no earlier or same event matched `b`;
     - false at the first event matching `b` if no earlier event matched `a`. An event matching both makes it false;
     - false at the end if neither ever matched.
   - **`unique(list)`:** settles when `list` settles, which is at the end for `all(…)`. A duplicate found during the stream is reported at the end, not earlier. Tracking per-match values incrementally is left out of M9. Two items are equal when the capture language's `==` says so: canonical JSON with sorted keys and every integer digit.
   - **When the run ends:** everything is known, and every pending check settles.
   - **A run that does not complete** fails every pending check with a reason:
     - "the request was stopped before this check settled" (cancelled);
     - "the request failed: MESSAGE" (failed);
     - "the request was not sent" (blocked).

     Settled checks keep their result.
3. **How terms are evaluated: internal captures through `CaptureTracker`.**
   - **Terms:** each term `t` becomes an internal `CaptureDefinition` named by the term's own text (identical terms share one), with expression `t | json` and `secret: false`, so a failure reason that quotes the name reads naturally.
     - Its resolved text is parsed back with `parseJson`, which is lossless. A failure keeps its reason.
     - Terms never reach the capture registry, the strip, hints or variables.
   - **Counts and `before`:** each counted comparison and each `before` side becomes an internal `count(c)` definition, named `#count TEXT`, `#before-a TEXT` or `#before-b TEXT` so they never collide with a term.
   - **The new hook:** `CaptureTracker` gains `onProgress(name, index, count)`, called each time a `count` watch counts an event. For `before`, the `b` side is defined before the `a` side, so within one event the tracker reports `b` first; an event matching both is then false.
   - **Why:** this inherits the capture tracker's 10 ms slices, queue, backpressure, child-process hand-off and spill-file reads instead of duplicating them.
   - **Layers:** design section 5's `checks → expressions, events` row gains `capture (tracker)`.
4. **Details: expected and actual values.** Each failed or passed check carries one line of detail, with values as compact JSON, each cut to 200 characters and masked:
   - **A failed comparison:**
     - with a literal on the right: `got VALUE`, so the Checks view reads ``status == 201` got 500``;
     - with a literal on the left: the same with the right side's value;
     - otherwise: `LEFT is VALUE, RIGHT is VALUE`.
   - **A missing operand:** `TERM is missing: REASON`.
   - **Early count failures:** `count(…) reached N`.
   - **`before` failures:**
     - `type == "B" matched event 3 first` when `b` matched first;
     - `type == "A" and type == "B" matched the same event 3` when they matched together;
     - `no event matched type == "A"` when `a` never matched.
   - **`unique` failures:** `VALUE appears more than once`.
   - **`exists` failures:** `TERM is missing: REASON`.
   - **`!x` failures:** `TERM is VALUE`.
   - **Combinations:**
     - `&&` gives the detail of its first false side;
     - `||` gives the details of its sides joined with `; `;
     - a passed check has no detail.
5. **Where results show.**
   - **Checks tab:** one row per `# @expect` line, in file order, with its state (✓ passed, ✗ failed, … pending), the expression text and its detail. "No checks for this request." when there are none.
   - **Panel status line:** gains `· P/T checks`, where P is passed and T is all checks of the run.
   - **CodeLens and outcome text:** when the request has checks, start with `✓ ` if all passed or `✗ ` if any failed, and gain ` · P/T checks`, for example `✓ 200 OK · 120 events · 4.3 s · 5/5 checks`. Without checks they are unchanged.
   - **Editor decorations:** after each `# @expect` line of a visible `.http` editor, an after-text decoration shows the state:
     - `✓` in `testing.iconPassed`;
     - `✗ DETAIL` (detail cut to 80 characters) in `testing.iconFailed`;
     - `…` in `descriptionForeground`.

     The hover holds the full masked detail, at most 4,096 characters. A result is matched to the request's lines by expression text and occurrence order; a line edited since the run shows no decoration.
6. **Registry bounds:** the check registry keeps the latest run's results for at most 500 request keys, evicting like the capture registry, and releases a run's entries when the run leaves history.

## Review Focus

1. **An early verdict that differs from the end verdict**, the core of "never change after settling". Most likely from a term handed to the child process for a large event resolving after a later event, or a count that reaches a bound in a resumed slice. Pinned in Task 4 by a property test: for every scripted stream, each live verdict equals the verdict computed with all knowledge at the end.
2. **`before(a, b)` edge cases:**
   - `a` and `b` matching the same event;
   - `b` matching an event larger than 256 KiB;
   - neither matching;
   - a run cancelled between them.

   Pinned in Task 4.

3. **Count comparisons:**
   - every operator, with the literal on either side;
   - negative, decimal and 20-digit literals;
   - a count compared with another count or a non-literal, which must wait for the end.

   Pinned in Task 3.

4. **A run that does not complete,** or is re-run while its checks are pending: the pending checks fail with the decision 2 reasons, and the new run starts again from pending without the old run's results leaking in. Pinned in Task 4 and Task 5.
5. **A secret in a detail:** a check comparing a sensitive header, or a body echoing a `{{$secret}}` value, must show the value masked in the Checks tab, the hover, the CodeLens and the log. Pinned in Task 4 and Task 7.

### Task 3: Check compiler and three-valued verdicts

**Files:**

- Create:

**Interfaces:**

- Produces:

  ```ts
  export type Term =
    | { kind: 'value'; id: number; expr: Expr; text: string }
    | { kind: 'count'; id: number; condition: Expr | undefined; text: string }
    | { kind: 'before'; id: number; first: Expr; second: Expr; text: string };
  export interface CheckProgram {
    skeleton: Expr;
    terms: readonly Term[];
    text: string;
  }
  export function compileCheck(expression: Expr, text: string): CheckProgram;

  export type TermState =
    | { kind: 'pending' }
    | { kind: 'value'; value: Value }
    | { kind: 'missing'; reason: string }
    | { kind: 'count'; count: number; final: boolean }
    | { kind: 'before'; first: number | undefined; second: number | undefined; final: boolean };
  export type Verdict =
    { state: 'pending' } | { state: 'passed' } | { state: 'failed'; detail: string };
  export function verdictOf(program: CheckProgram, states: ReadonlyMap<number, TermState>): Verdict;
  export function canonicalKey(value: Value): string;
  ```

  The compiler builds terms as follows:
  - a `count(c)` that is an operand of a comparison with a number literal becomes a `count` term, and every other `count(…)` stays inside a `value` term;
  - each `before(a, b)` becomes a `before` term, whose `first` is `a` and `second` is `b`;
  - every other maximal value sub-expression becomes a `value` term.

  `verdictOf` replaces settled value terms with literal nodes and evaluates comparisons with the existing `evaluate()`, so `==`, `in`, `contains`, `startsWith` and `matches` keep their exact semantics.
