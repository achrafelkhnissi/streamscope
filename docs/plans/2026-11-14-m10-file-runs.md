# M10 File Runs in the Testing View Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** run a whole `.http` file as an end-to-end test. Each file is a suite in VS Code's Testing view and each request a test with a gutter run button. A file run sends its requests in file order, one at a time, and reports passed, failed (with each failed check), errored or skipped (with the reason). Stopping the run cancels the active request. `# @until` ends a stream at the first matching event.

**Architecture:**

- **Pure core (`src/runs`):**
  - `file-run.ts` turns one request's final snapshot and check results into a verdict, and runs a list of requests one at a time with cancellation;
  - `until.ts` tests each event against the `# @until` condition, and `run.ts` ends the run at the first match.
- **Skip rule from the resolver:**
  - every request of a file run is started, so a producer that fails, is blocked or is stopped fails its captures, as it already does;
  - a dependant is then blocked by the resolver, and its problem now names the producer run (`producerRun`);
  - the file run skips it when that run belongs to the same file run.

  No second dependency analysis is written.

- **Check completion:** `CheckRegistry.settled(key, runId)` resolves once every check of a run has settled, so the verdict waits for checks that settle after the response ends.
- **VS Code layer (`src/vscode/testing`):**
  - one `TestController` with a default Run profile;
  - test items for open documents and for workspace files;
  - a run handler that starts each request through the same path as Send Request, without opening panels or toasts, and reports to the `TestRun`;
  - the command `Streamscope: Run File`.

**Tech Stack:** TypeScript 6.0.3, VS Code Testing API 1.101 (`tests.createTestController`, `TestRunProfile`, `TestRun`, `TestMessage`), Vitest, `@vscode/test-cli`. No new dependency.

## Decisions this plan makes (builder's call, approval of this plan approves them)

1. **The test tree.**
   - **Files:** one test item per `.http` or `.rest` file: id = the document URI, label = `workspace.asRelativePath(uri)`, `uri` set, `canResolveChildren` true until its requests are known.
   - **Requests:** one child per request:
     - **Fields:**
       - id = the request key (`requestKey`, the identity runs, captures and checks already use);
       - label = `requestLabel(request)`;
       - `description` = `METHOD maskUrl(url)` when the label is a name or a title;
       - `range` = `request.range`, which gives the gutter button;
       - `sortText` = the request's index padded to 5 digits, so the Testing view keeps file order instead of sorting by label.
     - **Duplicate `# @name`:** a request whose key repeats an earlier one in the file gets the id `KEY\n#INDEX`. A file run reports it errored with "Another request in this file is also named NAME."
   - **Discovery:**
     - open `http` documents (`file` and `untitled` schemes) get their items at once and follow every edit, reusing items by id;
     - workspace files come from `workspace.findFiles('**/*.{http,rest}')`, which respects `files.exclude`, capped at 1,000 files (`maxTestFiles`), plus a `FileSystemWatcher` for created, changed and deleted files;
     - a closed file's requests are read and parsed with `parseHttpFile` when VS Code resolves the item, and when the file changes on disk after that;
     - an item for an open document outside the discovered files is removed when the document closes;
     - `refreshHandler` runs discovery again.
   - **Activation:** `workspaceContains:**/*.http` and `workspaceContains:**/*.rest` join `activationEvents`, so the Testing view lists files before one is opened.
   - **Trust:** the controller exists only in a trusted workspace, and is created when trust is granted. In a restricted workspace `Streamscope: Run File` shows "File runs need a trusted workspace. Trust it to run requests from the Testing view."
2. **Running.**
   - **Profile:** one Run profile, labelled "Run", default. No Debug or Coverage profile.
   - **Order:** included request items are grouped by file. Files run in the order of their relative paths, and requests in file order, one at a time. Each request reaches a terminal state, and its checks settle, before the next starts. Excluded items are left out.
   - **What a run uses:** the file's text when the run starts: an open document's text (saved or not), otherwise the file on disk, opened with `workspace.openTextDocument`. Edits during a run apply to the next run.
   - **No panels or toasts:** file runs start requests through the same path as Send Request, with `reveal: false`:
     - a request whose response panel is open shows the new run there without taking focus;
     - no panel opens for the others;
     - blocked requests show no notification, since the Testing view reports them.

     Runs still go to history, the log, the CodeLens and the decorations.

   - **Run File:** `Streamscope: Run File` (`streamscope.runFile`, icon `$(run-all)`, Command Palette when `editorLangId == http`) runs the active file's item through the same handler, with a `TestRunRequest` the extension creates.
   - **Several runs at once:** separate file runs may overlap. A request started by a second run cancels its earlier run, as Send Request does, and the first run reports it skipped.
3. **Results.** Each request gets `started`, then exactly one of these:

   | Outcome                                                                       | Report                                                                                               |
   | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
   | `completed` and every check passed (any HTTP status, no checks counts)        | `passed(item, elapsedMs)`                                                                            |
   | `completed` and a check failed                                                | `failed(item, messages, elapsedMs)`, one `TestMessage` per failed check                              |
   | `failed` (transport, `# @timeout`, body too large, `# @until` work limit)     | `errored(item, message, elapsedMs)` with `run.failure.message` at the request line                   |
   | `blocked` with a problem whose `producerRun` belongs to this file run         | `skipped(item)`, and the output line gives the reason                                                |
   | `blocked` otherwise (undefined variable, invalid expression, earlier failure) | `errored(item, message)` with the problems' messages joined by a space, at the first problem's range |
   | `cancelled` by stopping the file run                                          | `skipped(item)`, output "The file run was stopped."                                                  |
   | `cancelled` otherwise (Stop Request, or a newer run of the request)           | `skipped(item)`, output "The request was stopped." The file run goes on                              |
   | not started (settings error, dismissed secret prompt, duplicate name)         | `errored(item, message)`                                                                             |
   - **A failed check's message:** `` `TEXT` DETAIL ``, for example `` `status == 201` got 500 ``, located at the check's `# @expect` line as parsed when the run started. A pending check at the end cannot happen, because M9 settles every check of a completed run.
   - **Output:** after each request, one line `LABEL: describeOutcome(snapshot, summary)` (masked), for example `startRun: ✓ 200 OK · 5 events · 0.1 s · 3/3 checks`. A skip adds `LABEL: skipped. REASON`. Lines end in `\r\n`, as `appendOutput` requires, and carry the request's location and item.
   - **Not run:** requests after a stop get no report. `TestRun.end()` resets them, which the Testing view shows as not run.

4. **The skip rule: `producerRun` on resolution problems.**
   - `ResolutionProblem` gains `producerRun?: number`, the id of the run whose capture or response the request needed and could not get. It is set for:
     - a failed capture from the registry (`lookupResult`);
     - a failed response reference;
     - a wait that timed out on a producer run.

     It is not set for undefined variables, own-capture reasons, cycles or producers that never ran.

   - A request is skipped when one of its problems names a run started by this file run. A chain therefore skips through: if A fails, B is blocked by A's failed capture and skipped, then C is blocked by B's captures (which failed because B was not sent) and is skipped too.
   - A capture that failed before the file run (an earlier Send) gives an errored request, not a skipped one.
5. **`# @until`.**
   - **The condition:** the argument of the request's last `# @until` line is parsed as an event condition, as for `first(…)`. An invalid condition already blocks the request with its diagnostic, and an empty `# @until` (`empty-until`) now blocks it too.
   - **When it is tested:** on every `json` and `text` event, after captures and checks have seen the event, with a work budget of 500,000 units (`hostEvaluationUnits`), restarted per event.
   - **On the first match:**
     - the run stops its stream session and closes the connection;
     - events after the matching one, even in the same chunk, never reach the store, the reply, captures or checks;
     - the run ends `completed` with `untilEvent` set to the event's index, so captures and checks see a completed run whose last event is the match;
     - raw bytes after the match that already arrived stay in Raw, which shows what was received.
   - **Work limit:** a condition that runs out of work fails the run with "# @until needs too much work for event N, so Streamscope stopped the request.", kind `until-work`.
   - **Where it shows:** the panel status line adds "ended by # @until at event N".
   - **Without events:** `# @until` on a response without events (a JSON body or plain text) has no effect.
6. **`# @timeout`** has been enforced since M2 as the transport's total limit. M10 adds an integration test showing a timed-out request reported as errored with that message.
7. **Check completion signal:** `CheckRegistry.settled(key, runId): Promise<readonly CheckEntry[] | undefined>`.
   - It resolves once every check of `runId` has settled, with its entries.
   - It resolves at once with `[]` when the key has no entries, because the run had no checks.
   - It resolves `undefined` when a newer run of the key begins or the key is evicted while waiting. The file run then reports errored with "A newer run of this request replaced its check results."
   - A waiter is removed when it resolves.

## Review Focus

1. **Skip chains and their boundary:**
   - producer failed, blocked, stopped, or capture not matched;
   - a dependant two steps away;
   - a dependant reading the producer through `{{name.x}}`, a bare `{{x}}` and `{{name.response.body.$.id}}`;
   - against these, a dependant whose failed capture came from a Send before the file run, which must be errored, not skipped.

   Pinned in Task 2 (problems carry the run), Task 4 (verdicts) and Task 7 (integration).

2. **`# @until` at every chunk boundary,** for NDJSON and SSE: the matching event is the last one in the store, the reply and every observer, and `last(…)` captures read it. Pinned in Task 1.
3. **Stopping at awkward moments:**
   - while the active request waits for a capture;
   - between two requests;
   - before the first starts;
   - twice.

   No request starts after the stop, the active one is cancelled, and nothing is reported twice. Pinned in Task 4 and Task 7.

4. **Item identity under edits:**
   - a request added above others;
   - an unnamed request whose URL changes;
   - a duplicate `# @name`;
   - an untitled document.

   Ids stay unique, VS Code never sees a duplicate id, and a run uses the text at its start. Pinned in Task 6 and Task 7.

5. **Late results:** a check that settles after the response ends, such as `unique(all(…))` in the child process, and a request with no checks on a 500 response. The verdict waits for the first and passes the second. Pinned in Task 3, Task 4 and Task 7.

### Task 4: The file run core

**Files:**

**Interfaces:**

- Consumes:

- Produces:

  ```ts
  export interface FileRunStep {
    key: string;
    label: string;
  }
  export type RequestVerdict =
    | { kind: 'passed'; durationMs: number }
    | {
        kind: 'failed';
        durationMs: number;
        checks: readonly { index: number; text: string; detail: string }[];
      }
    | { kind: 'errored'; durationMs: number | undefined; message: string }
    | { kind: 'skipped'; reason: string };
  export type StepStart =
    | {
        kind: 'started';
        run: { id: number; done: Promise<RunSnapshot>; cancel(): void };
      }
    | { kind: 'not-started'; message: string };
  export interface FileRunHooks<S extends FileRunStep> {
    begin(step: S): void;
    start(step: S): Promise<StepStart>;
    checks(step: S, runId: number): Promise<readonly CheckEntry[] | undefined>;
    report(step: S, verdict: RequestVerdict, run: RunSnapshot | undefined): void;
  }
  export function requestVerdict(
    run: RunSnapshot,
    checks: readonly CheckEntry[] | undefined,
    fileRunIds: ReadonlySet<number>,
    stopped: boolean,
  ): RequestVerdict;
  export function runFile<S extends FileRunStep>(
    steps: readonly S[],
    hooks: FileRunHooks<S>,
    signal: AbortSignal,
  ): Promise<void>;
  ```

  `requestVerdict` follows decision 3's table. Its exact strings are:

  - "The file run was stopped."
  - "The request was stopped."
  - "A newer run of this request replaced its check results."

  `runFile` calls `begin`, `start`, `done`, `checks` and `report` for each step in order. It calls `checks` only for a `completed` run. It adds each started run's id to the set before awaiting it. On `signal` abort, it cancels the active run, reports it with `stopped: true`, and starts nothing more.
